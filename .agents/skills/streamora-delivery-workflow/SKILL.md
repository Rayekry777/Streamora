# Streamora 交付工作流

## 执行顺序

1. 完整读取 `docs/project/PROJECT_ROADMAP.md`、`docs/development/BACKEND_DEVELOPMENT.md` 和当前阶段验收文件。
2. 检查工作区、已有实现、验证记录和用户未提交改动，以事实校正阶段状态。
3. 只执行当前里程碑；按“契约、后端主链路、用户端与管理端、联调、验收”推进。
4. 涉及新方案、依赖或组件时，完整读取并执行 [开源方案优先政策](../../../docs/development/OPEN_SOURCE_ADOPTION_POLICY.md)，先调研成熟开源方案并记录结论。
5. 使用 [里程碑门禁](references/milestone-gates.md) 判断是否达到出口条件。
6. 使用 [状态规则](references/status-rules.md) 更新状态，禁止跳过“待验收”。
7. 按 [交付报告](references/delivery-report.md) 写入阶段验收文件并向用户报告。

## 强制约束

- 用户端与管理端按领域切片同步推进，后端契约领先半步。
- 未得到用户验收，不得把里程碑标记为“已完成”，也不得主动进入下一里程碑。
- 一个阶段未完成时，优先补齐本阶段缺口；不得用后续阶段的占位实现伪装完成。
- 不得跳过开源方案调研；自研必须在验收记录中说明无可采纳开源方案的证据与原因。
- 所有验证记录必须写明实际执行内容、结果和未验证项。
- 不代替用户提交或推送 Git，除非用户在当前请求中明确授权。

## Git 提交与中文总结

仅在用户当前请求明确授权 Git 提交时执行：

1. 先检查工作区和暂存区，保留不属于本次功能的用户改动。
2. 按可独立回滚和审阅的功能边界拆分提交。前端、后端必须分开提交；契约、迁移、验收或规范文档随其所属功能提交，禁止为凑数量拆分。
3. 每次暂存精确文件路径，执行 `git diff --cached --check`；提交前确认暂存内容只含该功能。
4. 提交信息必须使用中文 Conventional Commit 标题加正文；禁止只提交一行标题。范围使用所属领域，例如 `媒体`、`用户端`、`管理端`、`身份`。
5. 每条提交正文和提交后的总结均按以下模板提供明细；根据实际内容增减功能项，不得虚构验证结果。未执行的验证必须明确标为“未运行（原因）”。使用多个 `-m` 参数或提交信息文件写入标题和正文，确保 `git log` 可直接查看完整记录。

```text
feat(范围): 一句话说明本次功能

- 功能明细 1
- 功能明细 2
- 契约、迁移、测试或文档明细（如有）

验证结果：

- 实际执行的检查或测试及其结果
- 未运行项及原因（如有）
- 阶段状态：进行中 / 待验收 / 已完成
```

6. 提交后报告提交哈希、模板化中文明细和最终工作区状态；不得声称已推送，除非用户另行明确授权。
