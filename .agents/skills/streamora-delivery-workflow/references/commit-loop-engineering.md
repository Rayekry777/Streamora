# 提交前修复循环

## 触发与分组

在准备提交时，先读取工作区差异并按功能、所有权和运行边界分组。

- 后端：`services/`、`packages/`、后端契约、迁移和其测试。
- 用户端：`apps/web/` 及其用户端测试。
- 管理端：`apps/admin-web/` 及其管理端测试。
- 文档、基础设施、工作流：只在不属于上述功能提交时单独提交。

不得把前端与后端混入同一功能提交。不得携带无关的用户改动。

## 分支主线

每次开发前依次执行：

```powershell
git switch master
git fetch origin --prune
git pull --ff-only
git switch -c feature/<领域>-<主题>
```

`master` 只跟踪 `origin/master`，禁止在其上开发、提交、merge 或 rebase。人工 PR 来源只能是 `feature/*`，本机自动修复使用 `agent/*`，部署修复使用 `deploy-repair/*`；三类分支均只通过 PR squash 合并到 `master`。发现本地 `master` 分叉时，先归档或移出未合并工作，不能直接合并旧主线。

## 循环协议

1. 主 Agent 描述本次提交的边界、预期行为和所需验证，并完成主实现。
2. 启动一个独立子 Agent，传入功能范围、验证命令和当前差异；不得传入主 Agent 对故障原因的猜测。
3. 子 Agent 执行范围内的静态检查、单元或集成测试、构建和必要的契约检查。发现问题时，先最小化定位，再直接修改同一范围内的文件并重复验证。
4. 子 Agent 回报实际执行的命令、结果、修复文件、未运行项与外部阻塞。主 Agent 审阅其差异，重新执行受影响验证，并决定是否进入下一轮。
5. 本地错误仍存在时，继续该循环；同一外部阻塞重复出现三次时停止，保留日志并请求用户提供凭据、权限或基础设施处理。禁止把失败状态提交为“通过”。
6. 所有门禁通过后，主 Agent 复核 `git diff --check`、提交范围和提交正文，再创建提交。推送后监控 GitHub 验证；远端失败进入新的本地修复循环。

子 Agent 任务模板：

```text
你是本次功能提交的独立质量代理。验证 <功能范围>，不要假设故障原因。
仅修改该范围内为通过验证所必需的最小文件；不得提交、推送、回退其他改动、修改密钥或扩大需求。
执行 <验证命令>。失败时复现、修复并重复执行。最后报告实际命令、结果、修改文件、未运行项和外部阻塞。
```

## 验证选择

| 改动范围 | 至少执行 |
|---|---|
| 后端服务、契约或迁移 | `bash ./mvnw -B -ntp verify`，并执行受影响服务集成测试 |
| 用户端或管理端 | `pnpm typecheck`、`pnpm lint`、`pnpm test`、`pnpm build` |
| 前后端接口 | OpenAPI 生成与校验、受影响前端测试、真实接口或契约测试 |
| Docker/Compose/部署 | 对应 Compose 配置校验、镜像构建或 GitHub 部署诊断规定的检查 |

本机没有 Docker 时，提交前仍执行可运行的静态与单元验证，并把 Docker 检查明确列入“未运行项”；推送后的“功能 Docker 验证”必须在 GitHub 托管 Runner 通过。阶段分支只有在当前 SHA 的功能验证通过、转为非 Draft 并添加 `stage:ready` 后，才运行虚拟机累计验收。

按改动风险增加 E2E、安全和性能检查。无法执行的检查必须写入“未运行项”并说明原因。

## 强制提交格式

创建前执行 `git diff --check`。提交后执行 `git log -1 --format=%B`，确认正文含四个区块且每个区块有实际内容。

```text
<type>(<范围>): <中文摘要>

功能明细：
- <实际变更 1>
- <实际变更 2>

验证结果：
- <实际命令或 GitHub 工作流>：通过

未运行项：
- 无

阶段状态：
- 阶段 <N>：进行中
```

`type` 只使用 `feat`、`fix`、`refactor`、`test`、`docs`、`build` 或 `ci`。不要使用单行提交；不要把计划写成已验证结果。
