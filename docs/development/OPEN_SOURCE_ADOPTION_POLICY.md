# Streamora 开源方案优先政策

## 适用范围

所有新的产品能力、基础设施、SDK、组件库、算法、媒体处理、协议实现、Agent 框架、可观测性与安全能力，必须先在网上调研成熟开源方案。仅当没有满足需求的方案，或现有方案无法在许可证、安全、性能、兼容性或维护成本上满足项目边界时，才允许自研。

## 决策流程

1. 明确功能目标、非功能约束、数据边界、运行环境和许可证要求。
2. 使用官方网站、代码仓库、发行说明、漏洞公告和许可证原文调研至少两个候选方案；优先使用项目官方文档和源仓库作为证据。
3. 按 [评估维度](#评估维度) 记录候选方案、证据链接、版本、许可证、采用结论与替代方案。
4. 选择满足要求且维护可靠的开源方案，先做最小可行集成和针对性验证，再纳入正式实现。
5. 只有在评估结论为“无可采纳方案”时自研；记录缺口、拒绝原因、范围、替换边界和后续复审日期。

## 评估维度

| 维度 | 最低要求 |
|---|---|
| 功能与边界 | 满足当前用例，不突破服务数据归属、隐私或安全边界 |
| 许可证 | 与商业闭源交付兼容；禁止未经法务确认引入强 Copyleft 依赖 |
| 维护与社区 | 有稳定发布、清晰文档、公开问题跟踪和持续维护迹象 |
| 安全 | 可获得安全公告和版本修复；不存在未接受的高危漏洞 |
| 兼容性 | 兼容 Java 21/Spring Boot 3.5、Vue 3/Vite、Docker 运行环境及既有协议 |
| 性能与运维 | 可以满足目标指标，支持监控、日志、升级和故障恢复 |
| 退出成本 | 用项目接口或适配器隔离，不把供应商或库类型扩散到业务层 |

## 决策记录模板

在对应阶段验收文件或设计决策记录中填写：

| 项目 | 内容 |
|---|---|
| 需求 | 功能与硬约束 |
| 候选 | 名称、版本、官方网站/仓库链接 |
| 证据 | 许可证、维护、安全、兼容性与性能证据链接 |
| 结论 | 采用、暂不采用或自研 |
| 理由 | 与评估维度对应的简短理由 |
| 隔离方式 | 接口、适配器、回滚或替换策略 |
| 验证 | 实际执行的测试、基准或演示结果 |

## 禁止事项

- 不得因“自己实现更快”跳过调研和记录。
- 不得仅凭星标数量、博客转载或二手资料判断成熟度。
- 不得引入许可证不明、无人维护、存在未处理高危漏洞或与项目基线不兼容的依赖。
- 不得直接复制受保护的品牌、素材、界面或私有 API；开源代码也必须遵守其许可证与署名要求。
