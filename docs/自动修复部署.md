# Streamora 部署与本机修复

`master` 每次推送先执行“验证”。验证通过后，标签为 `streamora-core` 的虚拟机 Runner 从 Actions checkout 的精确提交构建并部署 `core` Profile。虚拟机 `/opt/streamora/platform/compose/.env` 只在 Compose 启动时读取，绝不进入 Git、镜像、诊断或本机 Loop 工作目录。

部署成功会把 SHA 写到 `~ub001/.local/state/streamora/last-healthy.json`。Compose 健康检查和 Runner 上的 Playwright 浏览器联调都通过后才记录健康版本。失败时保留脱敏诊断 Artifact；两个版本之间没有 `db/migration` 变更时，部署脚本自动恢复最后健康镜像。

## 职责边界

- GitHub Actions：验证、部署、浏览器联调、回滚和脱敏诊断。
- 本机 Codex CLI：读取失败日志与 Artifact、在 `D:\aitool\loop-state\repository` 隔离副本中生成最小修复、验证、创建 PR、启用自动合并并继续等待部署结果。
- GitHub Actions 不再调用 DeepSeek、Codex Action 或任何模型，也不再保存修复用 API Key/PAT。

## 使用方式

先完成本机工具与认证初始化：

```powershell
. .\scripts\ops\Initialize-StreamoraToolchain.ps1 -RequireCodex
.\scripts\ops\Test-StreamoraToolchain.ps1 -RequireCodex
```

对现有 PR 启动闭环：

```powershell
.\scripts\ops\Start-StreamoraLoop.ps1 -Pr 123
```

对已标记 `agent:ready` 的 Issue 创建实现 PR：

```powershell
.\scripts\ops\Start-StreamoraLoop.ps1 -Issue 123
```

恢复已登记任务的轮询：

```powershell
.\scripts\ops\Start-StreamoraLoop.ps1 -Watch
```

守护仅在命令窗口运行期间活动。它先验证 `gh` 与 `codex` 登录，使用 GitHub 凭据管理器推送分支，从不保存 Token。用户当前工作区不会被守护修改。

## 本机分支规范

`master` 只跟踪 GitHub 的 `origin/master`，不用于本地开发。开始人工开发前执行：

```powershell
git switch master
git fetch origin --prune
git pull --ff-only
git switch -c feature/<领域>-<主题>
```

人工 PR 只允许 `feature/*`，本机 Codex 自动任务使用 `agent/*`，部署修复使用 `deploy-repair/*`；它们都只能通过 PR squash 合并到 `master`。如果 `git pull --ff-only` 提示 `master` 分叉，先将本地未合并工作归档或迁入新的 `feature/*` 分支，再同步主线，不能在 `master` 上直接 merge 或 rebase。

## 修复与终止

首次验证或部署失败立即进入本机 Codex CLI 修复。每个根提交最多三次尝试；每次必须通过 Git diff、禁止路径、提交元数据和受影响的本机验证，再推送 PR。最新 SHA 的三个 GitHub 检查成功后，守护使用受保护的自动 squash 合并。

无安全补丁、本机验证失败或第三次仍未成功时，守护停止写入并创建去重的 `agent:blocked` Issue，附带根提交、尝试次数、Actions 运行链接与本地诊断位置。守护不读取 `.env`、密钥、迁移、锁文件或持久卷。

## 本地浏览器访问虚拟机

首次为 `ub001` 配置私钥后运行：

```powershell
.\scripts\ops\open-streamora-tunnel.ps1
```

然后访问 `http://127.0.0.1:3000` 和 `http://127.0.0.1:3001`。关闭窗口或按 `Ctrl+C` 即停止隧道。
