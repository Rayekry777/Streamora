# Streamora 自动修复部署

`master` 的每次推送先执行“验证”。验证通过后，标签为 `streamora-core` 的虚拟机 Runner 从 Actions checkout 的精确提交构建并部署 `core` Profile。虚拟机上的 `/opt/streamora/platform/compose/.env` 只在 Docker Compose 启动时读取，绝不进入 Git、镜像或日志。

部署成功会把 SHA 写到 `~ub001/.local/state/streamora/last-healthy.json`。Compose 健康检查通过后还会在 Runner 上运行 Playwright Chromium，访问真实用户端与管理端，验证注册、宠物切换、管理员登录、运营概览和会话隔离；只有浏览器联调也通过才记录健康版本。失败时保留脱敏诊断与浏览器报告 artifact；若两个版本间没有 `db/migration` 变更，会以记录的 SHA 镜像无构建回滚。迁移发生变化时不会自动回滚数据库。

## 一次性配置

1. 在 GitHub 仓库 Settings 的 Actions/General 中，保留默认 Workflow permissions 为“Read repository contents and packages permissions”。在 General 中启用 Auto-merge；不需要开启 “Allow GitHub Actions to create and approve pull requests”，修复流程不会使用默认 `GITHUB_TOKEN` 创建或批准 PR。
2. 在 GitHub 仓库 `Settings -> Secrets and variables -> Actions` 中仅添加以下三个 Secret。工作流不读取本地配置文件，也不会把它们写入日志、补丁或 Artifact。
   - `DEEPSEEK_API_KEY`：仅用于第 1 至 3 轮 DeepSeek 最小补丁。
   - `OPENAI_API_KEY`：仅用于第 4 轮隔离 Codex 根因子 Agent。
   - `DEPLOY_REPAIR_GITHUB_TOKEN`：专用 GitHub 账号的细粒度 PAT，仅授予该仓库 Contents: Read and write、Pull requests: Read and write、Issues: Read and write、Checks: Read 权限；用于推送修复分支、创建 PR 和自动合并。
4. 在虚拟机以 `ub001` 登录，确保 Docker 已运行，并执行 `sudo usermod -aG docker ub001` 后重新登录。
5. 在仓库 Settings / Actions / Runners 创建 Linux x64 注册令牌，然后在虚拟机执行：

```bash
cd /opt/streamora
git pull --ff-only
platform/runner/install-github-runner.sh https://github.com/Rayekry777/Streamora.git <临时注册令牌>
```

5. 确认 `systemctl status actions.runner.*` 为 running，并在 GitHub Runners 页面看到在线的 `streamora-core` 标签。

注册令牌通常短时有效，不能保存到 Shell 历史、配置文件或仓库中。

## 首次部署

在 GitHub Actions 页面选择“部署 Core”，点 Run workflow，`ref` 填 `master`。首次成功应出现 Core 服务健康、前端 `/healthz`、网关与 identity readiness 通过，并生成状态文件。

Runner 完成注册后，日常更新只需推送到 `master`；不要再在 `/opt/streamora` 手工拉取源码。Runner checkout 才是部署构建来源。

## 每个阶段的使用方式

从 `master` 创建 `feature/phase-<阶段>-<主题>`，先完成本地验证，再推送并创建 PR。PR 的“验证”通过后合并到 `master`，随后会自动执行虚拟机部署和浏览器联调。完整清单见 [阶段发布验收清单](acceptance/PHASE_RELEASE_CHECKLIST.md)。

虚拟机端口仍只监听 `127.0.0.1`。需要在本机人工查看联调结果时，先配置 `ub001` 的 SSH 私钥，然后在仓库根目录执行：

```powershell
.\scripts\ops\open-streamora-tunnel.ps1
```

在本机浏览器打开 `http://127.0.0.1:3000` 和 `http://127.0.0.1:3001`。按 `Ctrl+C` 停止隧道。

## 自动修复边界

部署失败会触发“修复部署失败”。前三轮为最小修复，每轮必须重新通过验证后才自动 squash 合并；第三轮后仍失败时，独立根因 Agent 创建第四轮修复。合并会再次触发部署。代理仅可修改应用、Docker、Compose 与部署脚本，不能修改 `.env`、密钥、数据库迁移、依赖锁、GitHub Actions 工作流或持久卷删除逻辑。

缺少当前轮次所需的 Secret 时，流程不会尝试生成补丁，而是创建一个去重的配置诊断 Issue；填入后从失败运行重新执行即可。第 1 至 3 轮由 DeepSeek 生成受限统一补丁；第 4 轮由隔离的 Codex 根因子 Agent 实际修改工作树，再由外层工作流执行边界校验、创建提交和推送。每轮均会经过 Git diff、禁止路径和验证门禁；第四轮仍失败后会创建 Issue 并停止自动修改。不要在 `master` 人为制造故障来测试这一流程；使用独立临时分支验证 PR、验证、合并与上限行为。
